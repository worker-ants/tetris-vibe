**[CRITICAL] 랭킹 로직 중복 구현 (DRY 위반)**
- 위치: `lib/multiplayer/broadcast.ts:calculateRankings`, `server.mjs:checkRoundEnd`
- 상세: dense ranking(동점 동순위) 로직이 클라이언트(`broadcast.ts`)와 서버(`server.mjs`)에 각각 독립적으로 구현되어 있습니다. 클라이언트 `calculateRankings`는 `RankingEntry[]`를 반환하는 반면, 서버의 `checkRoundEnd`는 인라인으로 동일 로직을 재구현합니다. 두 구현이 동일한 결과를 내야 한다는 암묵적 계약이 있으나, 한 쪽이 변경될 때 다른 쪽이 갱신되지 않을 수 있습니다. 현재도 서버는 `playerId`를, 클라이언트 타입은 `id`를 사용하는 미묘한 차이가 있습니다.
- 제안: 랭킹 로직을 `lib/multiplayer/broadcast.ts`에 단일 구현으로 두고, 서버에서 `import`하여 사용하거나, `lib/multiplayer/ranking.ts` 같은 공유 모듈로 분리하세요. 단, `server.mjs`가 ESM이고 `lib/`가 TypeScript이므로 빌드 파이프라인 고려가 필요합니다.

**[CRITICAL] `isHost` 이중 소스 진실(Dual Source of Truth)**
- 위치: `app/hooks/useMultiplayer.ts:48`, `app/hooks/useMultiplayer.ts:connect()`
- 상세: `isHost`는 `useState(options.role === "host")`로 초기화되지만, `host_transferred` 수신 시 동적으로 변경됩니다. 그러나 `connect()` 내부에서는 여전히 `optionsRef.current.role`을 읽어 WebSocket 연결 시 메시지 타입(`create_session` vs `join_session`)을 결정합니다. 이는 런타임에 게스트가 호스트 권한을 가져도 `role`은 여전히 `"guest"`인 불일치 상태를 만듭니다. 현재는 `connect()`가 마운트 시 1회만 호출되므로 실용적 문제는 없지만, 구조적으로 `role`과 `isHost`가 서로 다른 의미를 갖게 됩니다.
- 제안: `isHost`를 `options.role === "host"`와 `players` 배열에서 파생하는 파생 상태(derived state)로 전환하거나, `role`을 완전히 제거하고 `isHost`를 단일 진실로 유지하세요.

**[WARNING] `state_broadcast` 프로토콜 변경의 타입 레벨 미반영**
- 위치: `lib/multiplayer/types.ts:ServerMessage`, `app/hooks/useMultiplayer.ts`의 `state_broadcast` 핸들러
- 상세: 서버가 이제 전체 상태 맵 대신 변경된 단일 플레이어 상태만 전송하지만(`{ [playerId]: state }`), `ServerMessage` 타입의 `state_broadcast`는 여전히 `states: Record<string, BroadcastState>`로 정의되어 있습니다. 구현 변경이 타입에 반영되지 않아, 타입만 보고는 "항상 모든 플레이어 상태가 온다"고 오해할 수 있습니다. 클라이언트가 증분 병합을 하는 이유도 타입이 아닌 주석에만 의존합니다.
- 제안: 주석 대신 타입으로 의도를 표현하세요. 예: `states: Partial<Record<string, BroadcastState>>`로 변경하거나, 증분 업데이트 전용 메시지 타입(`state_partial_broadcast`)을 분리하는 것이 명확합니다.

**[WARNING] Origin 검증의 런타임 의존성**
- 위치: `server.mjs:wss.on("connection")` Origin 검증 블록
- 상세: `allowedOrigins`가 각 WebSocket 연결 시 `getLocalIP()`를 호출하여 동적으로 구성됩니다. IP가 DHCP 갱신으로 변경되면 서버 재시작 없이 새 IP의 연결은 거부될 수 있습니다. 또한 `origin` 헤더가 없는 경우(`if (origin && ...)`) 검증을 통과하는데, 이는 비브라우저 클라이언트(curl 등)를 허용합니다.
- 제안: 서버 시작 시 `allowedOrigins`를 1회 캐싱하고, origin이 없는 경우에 대한 정책을 명시적으로 결정하세요.

### 요약

이번 변경은 코드 리뷰 피드백을 성실하게 반영한 결과로, 보안 강화(Origin 검증, 메시지 크기 제한, 입력 sanitization), 성능 최적화(증분 상태 브로드캐스트, 캔버스 Effect 분리, 배치 그리기), 버그 수정(stale closure, 중복 연결, 호스트 이탈 처리)이 잘 이루어졌습니다. 다만 아키텍처 관점에서 두 가지 핵심 문제가 남아 있습니다: `server.mjs`가 단일 파일에 너무 많은 책임을 집중시키는 God Object 패턴으로 진화하고 있으며, 랭킹 로직의 클라이언트-서버 중복 구현이 DRY 원칙을 위반합니다. `isHost`의 이중 소스 진실 문제는 현재는 실용적 결함을 유발하지 않지만 구조적 취약성이며, 프로토콜 변경이 타입에 미반영되어 있어 계약 기반 개발의 장점이 희석됩니다. 전반적으로 이 규모의 프로젝트에서 허용 가능한 수준이나, `SessionManager` 추출과 공유 랭킹 모듈화가 우선 개선 과제입니다.
